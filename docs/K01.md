# K01 — Isolated runner for a bounded coding task

**Status:** Accepted
**Builds on:** ADR-11 in [ARCHITECTURE.md](ARCHITECTURE.md), which records that
"true isolation needs a process boundary, which is not part of this task."
K01 adds that boundary for one narrow use case.

## Why

The agent framework can now execute a model's tool calls under an execution
policy, but it cannot safely run *code a model wrote*. The obvious first
attempt — `subprocess.run(..., timeout=5)` — stops one runaway process and
nothing else:

- it does not stop a child the sample spawns;
- it enforces no memory or CPU limit;
- it does not stop the sample writing to the host project;
- it does not stop the sample reading the host environment, including keys.

**A subprocess timeout alone is not isolation.** It is one control out of
several. This task supplies the rest for a bounded, offline coding task, and
states exactly which controls are enforced by the operating system and which
are cooperative Python-level guards.

## The bounded task

`solution.py` must implement one pure function:

```python
def slugify(text: str) -> str
```

Rules: lowercase; keep ASCII `a-z0-9`; replace each maximal run of other
characters with one `-`; trim leading/trailing `-`; empty input → `""`.
The full contract with examples is `TASK_SPEC` in `coding_task.py`.

The acceptance tests (`ACCEPTANCE_TESTS`) were written from the contract, not
from a candidate solution. They test the rules one at a time — case, runs,
trimming, non-ASCII, digits, empty input, idempotence — so a partial
implementation fails a named test rather than the whole batch. A third,
independent implementation in the test suite checks that the documented
examples match the accepted behaviour.

The task is deliberately pure: it needs no network, no child process, no
clock, no random source and no file access. That makes the restriction
defensible rather than arbitrary — a correct solution never notices it.

## Architecture

```
host process                          sandbox process (new interpreter)
────────────                          ────────────────────────────────
run_python(source, tests)
  ├─ create temporary directory  ──▶  solution.py
  │                                   acceptance_tests.py
  │                                   _harness.py
  ├─ scrub environment               
  ├─ Popen(..., stdin=PIPE)      ──▶  waits on stdin (no code has run yet)
  ├─ attach OS limits (job/rlimits)   
  ├─ send nonce over stdin       ──▶  installs audit hook, imports tests
  ├─ wait with wall deadline          runs test_* functions
  ├─ kill group/job on timeout   ◀──  prints nonce-tagged JSON report
  └─ parse report, classify           
```

The stdin handshake closes the race that a plain `Popen` would leave open: on
Windows the process is created normally, the job object is attached, *and only
then* is the sample allowed to import or execute anything. (The alternative,
`CREATE_SUSPENDED`, cannot be combined with the pipes and environment handling
this module needs without dropping to raw `CreateProcess`.)

The report line is tagged with a per-run nonce delivered on stdin, so a sample
that prints `__SANDBOX_RESULT__...` at import time cannot be mistaken for the
harness. The nonce is not written to any file inside the sandbox.

## Controls

| Requirement | Mechanism | Strength |
|---|---|---|
| Ephemeral environment | `tempfile.TemporaryDirectory`; all files written there; removed afterwards | OS |
| No inherited secrets | child env is rebuilt from a small allowlist; any name containing KEY, TOKEN, SECRET, PASSWORD, PASSWD, CREDENTIAL, AUTH or PRIVATE is dropped; HOME/TEMP/USERPROFILE point into the sandbox | OS (the parent never puts them in the child) |
| Limited filesystem | audit hook refuses `open` for write outside the sandbox root and refuses `remove`, `rename`, `mkdir`, `chmod`, `truncate`, `link`, `symlink`, `utime` outside it; writes inside the sandbox are allowed | **cooperative** |
| No network by default | audit hook refuses `socket.connect`, `bind`, `getaddrinfo`, `gethostbyname`, `gethostbyaddr` | **cooperative** |
| No child processes | audit hook refuses `subprocess.Popen`, `os.system`, `os.exec*`, `os.spawn*`, `posix_spawn`; on Windows the job's `ActiveProcessLimit` backs this up | cooperative + OS |
| Wall-clock limit | `communicate(timeout=...)`, then job termination / process-group kill | OS |
| CPU limit | Windows job `PerProcessUserTimeLimit`; POSIX `RLIMIT_CPU` | OS |
| Memory limit | Windows job `ProcessMemoryLimit` + `JobMemoryLimit`; POSIX RSS watchdog (50 ms sampling) over the process group | OS / sampling |
| Process-count limit | Windows job `ActiveProcessLimit`; POSIX process-group kill on exit (no `RLIMIT_NPROC`) | OS in part |
| Fail closed | if the job cannot be created or assigned, the run is aborted; a missing or forged report is never "passed"; a test module with no tests is an error | — |
| No site-packages | interpreter starts with `-I -S -B`: isolated, no site, no bytecode writes; stdlib only | OS |

The interpreter is the base interpreter, not a venv launcher: a venv
`python.exe` on Windows spawns the real interpreter as a child, which
`ActiveProcessLimit=1` correctly refuses. The harness needs only the standard
library, so it does not need the venv.

### Platform verification

Both platform paths execute in the test suite, and both are verified:

- **Windows** — the full offline suite runs on Windows 11 / Python 3.11.9, so
  the job-object branch is genuine CI-independent evidence.
- **Linux** — the literal CI command (`pip install -r requirements-dev.txt &&
  pip install --no-deps -e . && ruff check . && pytest -m "not integration"`)
  runs in `python:3.11-slim`; 157 passed, 1 deselected. That run executes
  `setsid`/`killpg`, the rlimits, the RSS watchdog and the negative-returncode
  classification.

The first version of this branch was written and verified on Windows only. On
Linux the watchdog's `self._stop = threading.Event()` shadowed
`threading.Thread._stop()`, so every `watchdog.stop()` raised
`TypeError: 'Event' object is not callable` (25 failures). Renaming the
attribute to `_stop_event` fixed it; the tests were not skipped or altered. The
Windows branch never constructed the watchdog, which is exactly why a
Windows-only run could not find it — **CI on Linux is the authoritative check
for the POSIX path.**

After the fix there is no behavioural discrepancy between the platforms beyond
what the controls table already states: Windows enforces CPU and memory with a
hard job limit, Linux samples memory every 50 ms and enforces CPU with
`RLIMIT_CPU`. Those differences are mechanism, not semantics: the same samples
in `evidence/K01.md` are stopped on both, with the same fail-closed status rules.
macOS is not verified and its memory path is not enforced (no `/proc`).

## Threat assumptions

The runner assumes:

1. **The host is trusted**; the sample is not.
2. **The sample is Python source**, delivered as text. It may be wrong,
   hostile, or both. It may import anything the standard library offers.
3. **The acceptance tests are trusted.** They are supplied by the host, not by
   the sample. If an attacker controls the tests, the result is meaningless.
4. **The host process is healthy.** A local user who can ptrace/attach, edit
   the parent's memory, or replace the interpreter is outside the model.
5. **The task is honest.** A sample cannot pass by finding a bug in the
   *acceptance tests*; K01 does not protect against a subtly wrong oracle.

## Limitations — read before calling this a sandbox

- **The audit hook is not a security boundary.** It is a Python-level
  callback. Code that calls libc through `ctypes`, uses a native extension, or
  exploits an interpreter bug can bypass the filesystem, network and process
  guards. The OS limits (wall, CPU, memory, job process count) still apply to
  the process as a whole, but not the "no writes outside the directory" rule.
- **Writes are checked, reads are not.** A sample can read anything the host
  user can read, except that secret-looking environment variables are absent.
  It can read the host project and exfiltrate it only if it also has a channel
  out; the network guard is cooperative, so treat read access as real.
- **POSIX memory enforcement is sampled and Linux-only.** The watchdog polls
  `/proc` every 50 ms and kills the group on overrun; a fast allocator can
  exceed the limit between samples. On POSIX systems without `/proc` (for
  example macOS) the watchdog has nothing to read and memory is not enforced.
  `RLIMIT_AS` is deliberately not used because on 64-bit Linux it counts
  virtual address space and would break interpreter startup.
- **POSIX does not cap process count.** The sample's children are killed with
  the process group, but a sample can create a burst before the group is
  killed. Windows caps this in the job; POSIX does not.
- **Result integrity is not tamper-proof.** The nonce stops a naive forged
  report, but a sample that introspects the harness frame can read it. An
  in-process sample can also manipulate its own results. Tamper-proof grading
  belongs to the next wave (K02), not K01.
- **No Docker or VM backend.** The backend is the local machine's OS. If a
  container runtime were available, it would give a stronger filesystem and
  network boundary; it is not required here and is not attempted.
- **The harness is not hardened against interpreter-level attacks** (buffer
  overflows, `os._exit` tricks beyond fail-closed reporting, signal games).
  `os._exit(0)` is handled: no report means "killed", never "passed".
- **Only Python source is supported.** Native code, notebooks and dependency
  installation are out of scope.

## Alternatives considered

- **`subprocess` + timeout only.** Rejected: it is the problem statement. No
  memory bound, no filesystem bound, no process-tree bound.
- **Run in-process with `exec` and monkeypatched builtins.** Rejected: a
  sample can undo monkeypatches, and a crash takes the host with it. A process
  boundary is the minimum.
- **Docker/`nsjail`/`firejail`.** Stronger, but unavailable by default on a
  developer machine and impossible to test hermetically here. The interface
  (`run_python`) leaves room for a backend that shells out to one.
- **`RLIMIT_AS` on POSIX.** Rejected after measuring: virtual address space is
  much larger than resident memory on 64-bit Python, so a limit low enough to
  matter breaks startup. The watchdog measures resident memory instead, and
  the limitation is stated rather than hidden.
- **`CREATE_SUSPENDED` on Windows.** Rejected: it needs the whole spawn path
  reimplemented with raw `CreateProcess` to keep the pipes and environment;
  the stdin handshake achieves the same ordering with `Popen`.
- **Trusting a sample's self-report.** Rejected: a sample cannot mark its own
  homework. Results come only from the host-supplied acceptance tests, the
  nonce-tagged report and the OS exit status.

## Operating notes

```python
from gem_agentic_ai.coding_task import run_submission
from gem_agentic_ai.sandbox import SandboxLimits

result = run_submission(candidate_source, limits=SandboxLimits(wall_seconds=5))
print(result.status)          # passed / failed / timeout / killed / error
print(result.tests)           # per-test outcomes
print(result.isolation)       # what was actually enforced, per platform
```

`SandboxResult.status` is the contract: only `passed` means every acceptance
test ran and passed. Everything else is a refusal or a failure, and none of
them is silently treated as success.
