# A06 — A real MCP tool server

Status: implemented on `task/A06-mcp-tool-server`, based on `52e9398` (main
after A02, A03 and K01). This document records what the server is, how the
agent reaches it, which protocol revision is pinned, what the tests prove and
what the implementation does not establish.

## Why

The requirement is MCP, not "a tool endpoint". A FastAPI route that returns
JSON is not a Model Context Protocol server: it has no JSON-RPC framing, no
`initialize` handshake, no capability negotiation, no `tools/list` /
`tools/call` method set and no stdio transport. This task implements the
protocol with the official Python SDK and wires the existing LangGraph agent
to it **through the protocol**, not by importing the tool functions.

## What was built

| Component | Responsibility |
|---|---|
| `mcp_tools/server.py` | A real MCP server over stdio with two read-only tools |
| `mcp_tools/client.py` | Client bridge: `MCPToolset` (live session) and `MCPTool` (LangChain tool) |
| `mcp_tools/__main__.py` | `python -m gem_agentic_ai.mcp_tools --root <dir>` |
| `scripts/a06_demo.py` | End-to-end demo: handshake, direct calls, errors, agent runs |
| `tests/test_mcp_server.py` | Wire-level JSON-RPC tests plus in-process boundary tests |
| `tests/test_mcp_client.py` | Bridge tests and agent integration tests |

The server is a process. The agent launches it with
`StdioServerParameters`, speaks newline-delimited JSON-RPC 2.0 over its
stdin/stdout, and stops it when the session closes.

## The protocol

Pinned revision: **2025-11-25**. The SDK is pinned at `mcp==2.3.0`. The
client forces the legacy `initialize` handshake (`mode="legacy"`) and
**refuses to continue if the server negotiates any other revision**
(`ProtocolMismatchError`). The newer `2026-07-28` discovery flow is not
exercised; the pin is deliberate, and a version the bridge does not know is a
failure, not a best-effort attempt.

The handshake in the demo:

```
protocol: 2025-11-25 (pinned)
server: gem-agentic-ai-readonly 0.1.0
tools: search_files, read_file
```

A wire-level `initialize` request and response, as sent by the tests:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"wire-test","version":"0.0.0"}}}
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-11-25","capabilities":{"tools":{...}},"serverInfo":{"name":"gem-agentic-ai-readonly","version":"0.1.0"}}}
```

The SDK's `initialize` result advertises `tools`, `prompts` and `resources`.
This server registers only tools; `prompts/list` and `resources/list` return
empty lists, which a wire test asserts rather than leaves implicit.

After `notifications/initialized`, `tools/list` returns both tools with their
JSON Schemas, and `tools/call` returns a result envelope. A refused call is
`isError: true` with a text message; an unknown method is a JSON-RPC error
with code `-32601`; a malformed `tools/call` is a tool error.

## The tools

Both tools are read-only and confined to the directory passed as `--root`.

| Tool | Arguments | Returns |
|---|---|---|
| `search_files` | `query` (required), `glob_pattern` (default `**/*`), `max_results` (1–200, default 50) | `matches` with relative path, line and trimmed text; `truncated`; `files_scanned`; `files_skipped` |
| `read_file` | `path` (required), `max_bytes` (1–100 000, default 20 000) | relative `path`, `text`, `truncated`, `size_bytes` |

Boundaries:

- Absolute paths, drive-qualified paths and any `..` component are refused.
  The resolved path must be inside the resolved root, so a symlink cannot
  step out either.
- `glob_pattern` is relative and may not contain `..`; files that resolve
  outside the root are skipped.
- Files above 1 MB are skipped by search and refused by read.
- Files whose first 8 KiB contain a NUL byte are treated as binary: skipped
  by search, refused by read.
- Search walks at most 2 000 files, returns at most `max_results` matches,
  and says when it truncated.
- `.git`, `node_modules`, `__pycache__`, virtual environments, coverage and
  cache directories are excluded.
- Errors are raised as the SDK's `ToolError`, which the protocol carries as
  `isError: true` with the message intact. They are not exceptions that kill
  the server.

## How the agent reaches it

1. `MCPToolset` opens one stdio session and calls `tools/list`.
2. For each tool, `args_model_for` converts the MCP `inputSchema` into a
   Pydantic model. This is required by the existing `ToolGuard`, which
   refuses any tool without a Pydantic `args_schema`. A schema the bridge
   cannot represent (`anyOf`, `$ref`, an unsupported type) is refused at
   discovery rather than exposed unvalidated.
3. `MCPTool` is a LangChain `BaseTool` whose `_run` calls `tools/call` and
   whose `args_schema` is that generated model.
4. `build_agent(llm, toolset.tools)` wraps each one in the existing
   `GuardedTool`, so the MCP tools inherit the same validation, allowlist,
   timeouts, budgets, retries and audit trail as every other tool.
5. The model's tool call reaches the guard; the guard invokes the tool; the
   tool speaks MCP to the server process; the server's text result becomes
   the `ToolMessage` the model sees on its next turn.

One detail matters for correctness. `ToolGuard` executes every tool call in
a worker thread with a timeout, and an MCP session belongs to the event loop
that created it. The agent path therefore gives each call its own short-lived
stdio session (`_run` → `asyncio.run`). That costs a process spawn per call —
about 1.8 s for the whole one-call agent run in the demo, versus 70 ms for a
direct call on the already-open session on Windows (1.5 s versus 43 ms in the
same check on Linux) — and it keeps the thread/loop boundary honest. The
shared-session path is used by `MCPToolset.call_tool` and by async callers
that own the loop.

## Error handling

Three different failures, three different surfacings:

| Failure | Transport result | What the model sees |
|---|---|---|
| Deliberate refusal (empty query, path escape, oversized file) | `isError: true` with the message | `ToolMessage` with `status="error"` and the server's message |
| Unknown tool | `isError: true`, "Unknown tool: ..." from the server | At the agent, either the registry refuses an unregistered name (`guard.reject`, `CallStatus.REFUSED`) or the server's message reaches the model |
| Unexpected exception inside a tool | `isError: true` with a generic message; traceback on the server's stderr | `ToolMessage` with `status="error"` |

The bridge raises `MCPToolError` when `isError` is true. It does not return an
empty string, and the guard does not treat the call as a success. The tests
assert the error text is in the model's next context, so a regression that
swallowed it would fail.

## Tests

`tests/test_mcp_server.py` (15):

- 9 wire-level tests that spawn `python -m gem_agentic_ai.mcp_tools` and
  exchange raw JSON-RPC: handshake and pinned revision, capability
  advertisement with empty `prompts`/`resources` lists, `tools/list`
  schemas, a successful `tools/call`, unknown tool, invalid arguments, path
  escape, unknown method (`-32601`), and that the server keeps serving after
  a tool error.
- 6 in-process boundary tests: absolute path refused, escaped glob refused,
  schema constraints enforced, excluded directories skipped, `max_results`
  and truncation, and an invalid root rejected.

`tests/test_mcp_client.py` (16): discovery and schema conversion, protocol
mismatch refused, direct calls on the shared session, an awaited tool call,
read, unknown tool, tool error, path escape, binary and oversized files, the
guard's worker-thread path, enum/default/constraint conversion,
unsupported-schema refusal, an agent run that uses the MCP tool, an agent run
that receives a tool error as an error message, and an unregistered tool
refused by an agent registry.

Nothing in the suite uses the network. A subprocess and a temporary
workspace are the only dependencies.

## Demo

`scripts/a06_demo.py` creates a workspace, starts the real server, performs
the handshake, prints the negotiated revision and discovered tools, calls
both tools, exercises unknown-tool, path-escape and empty-query failures,
then runs the agent twice: once where the search succeeds, and once where
the server refuses the query. Every check must pass for the demo to exit 0.

## Acceptance criteria

| Criterion | Where it is proved |
|---|---|
| Protocol-correct request/response at a pinned version | Wire tests: `initialize`, `tools/list`, `tools/call`, `-32601`; `PROTOCOL_VERSION = "2025-11-25"`; `ProtocolMismatchError` on any other revision |
| The agent discovers and invokes a tool through the server | `test_the_agent_invokes_the_tool_over_the_protocol`; demo `agent` |
| Tool errors and unknown tools are handled, not swallowed | `test_a_tool_error_reaches_the_model_as_an_error_message`, `test_unknown_tool_is_a_tool_error`, `test_an_unknown_tool_is_refused_by_an_agent_registry`; demo `agent_tool_error`, `unknown_tool` |
| Tests run offline | Every test uses stdio and a temporary directory; the suite makes no network call |
| Not described as a plain HTTP endpoint | This document; the transport is stdio JSON-RPC and there is no HTTP server in the package |

## Alternatives considered

- **In-process tool functions.** Fastest, but it would not demonstrate MCP
  at all. The brief calls this out explicitly.
- **An HTTP JSON-RPC route.** MCP over streamable HTTP is a real transport,
  but it needs session management and HTTP infrastructure to prove the same
  point, and the brief warns against passing an HTTP endpoint off as MCP. The
  stdio transport is the protocol's original and simplest transport.
- **`mcp.server.fastmcp.FastMCP`.** Renamed in SDK 2.x; importing it raises a
  migration error. The server uses `mcp.server.mcpserver.MCPServer`.
- **Exposing the MCP `inputSchema` as a dict to LangChain.** The guard
  refuses tools without a Pydantic model, and a dict would skip validation.
  Schema conversion at discovery keeps the fail-closed rule.
- **One long-lived session for every agent tool call.** Correct only if the
  guard ran calls on the session's loop. It runs them on worker threads with
  timeouts, so each call gets its own session instead.
- **Returning `isError` as a normal string.** That would turn a failure into
  an observation the model could mistake for data. The bridge raises, and the
  guard marks the `ToolMessage` as an error.

## What this does not establish

- **The root is a path boundary, not a sandbox.** The server refuses paths
  outside its root; it does not restrict what the process itself may read, and
  it does not defend against a symlink swapped between the resolve and the
  open (a TOCTOU window). A hard link created inside the root is
  indistinguishable from a real file by path and is readable. K01 is the
  process-level isolation work; this is a read-only tool with a stated
  boundary.
- **No authentication.** stdio means the parent process is trusted. There is
  no token, no user identity and no multi-tenancy in the server.
- **Tools only.** No resources, prompts, sampling, elicitation, logging
  subscriptions or notifications are implemented.
- **One transport.** stdio only; no streamable HTTP, no SSE, no remote
  server.
- **A pinned revision.** The bridge pins 2025-11-25 and refuses anything
  else. It is not a general-purpose MCP client.
- **Per-call process cost.** The agent path pays a server start per tool
  call. The demo measures it; it is not a performance claim, and no effort
  was made to pool sessions across threads.
- **The guard still cannot kill a tool.** An MCP call that the guard times
  out keeps running in its thread and its server process is stopped when the
  session closes; the guard's thread is not interrupted. This is A03's
  limitation, inherited unchanged.
- **No concurrency test.** The tests are sequential. Two simultaneous agent
  calls would each start their own server; that is safe by construction but
  not measured under load.
- **Search is a substring scan.** It is not a ranked index, and a query that
  appears in a very large number of lines stops at `max_results` with
  `truncated: true`.
- **Test coverage of `server.py` is understated.** The module runs in a
  subprocess for the wire tests, so coverage.py cannot see those executions;
  it reports 62% for the module. The in-process tests cover the boundary
  helpers, and the wire tests cover the protocol behaviourally. Coverage is
  reported, not gated.
