# A03 — Bounded tool execution

Status: implemented on `task/A03-bounded-tool-execution`, based on `d3eed0f`.
This document records the design, the alternatives considered and the limits
of the implementation. It is deliberately narrower than the code comments:
those describe how the guard works, this describes what the task does and
does not establish.

## Why

Two problems motivated the task.

1. **The two agent paths disagreed.** A01 pinned a real divergence: an
   unexpected tool exception became an observation in the manual ReAct loop,
   while LangGraph's tool node re-raised it and ended the run. A task that
   claims bounded execution cannot leave that difference unexplained.
2. **Tool execution was unbounded.** The manual loop capped model turns only.
   Neither path validated arguments against the tool's schema, limited how
   long a tool could run, limited the number of calls, protected a
   side-effecting action, or told the caller why a run stopped.

### Call flow

`ToolGuard.execute()` applies the checks in this order:

1. **Allowlist** — the tool name must be in the registry passed to the agent.
   This check happens before a call slot is reserved, so a name the model
   invented cannot exhaust the budget.
2. **Budget reservation** — cancellation, deadline, total calls, per-tool
   calls, circuit state and observation-token budget. A refusal sets the
   run's first stop reason and is recorded as `refused`; it consumes no slot.
3. **Shape checks** — the arguments must be a mapping and must not exceed
   `max_argument_bytes` when serialised.
4. **Schema** — the tool must declare a Pydantic `args_schema`, and the
   arguments must validate against it. A tool without a schema is refused
   rather than run unvalidated.
5. **Idempotency** — if `(tool, action key)` already has a completed result,
   that result is returned with `cached=True` and the tool is not run.
6. **Approval** — a tool named in `consequential_tools` cannot run until its
   action key is in the `ApprovalStore`.
7. **Execution** — the call runs in a daemon thread and the guard waits at
   most `min(per_call_timeout_seconds, remaining_seconds)`.
8. **Record** — success, cache hit, error, timeout, refusal and approval
   refusal all produce a `CallRecord`; a successful result is written to the
   idempotency store.

`GuardedTool` adapts this to LangGraph. The tool node passes a tool-call
dictionary; the wrapper returns a finished `ToolMessage`, so the node passes
it through unchanged, including `status="error"`.

### Failure taxonomy

| Failure | Retried? | What the model sees |
|---|---|---|
| `ToolTimeoutError` (per-call timeout) | Yes, unless the tool is consequential | `Error during tool execution: ToolTimeoutError: ...` |
| `RetryableToolError` raised by the tool | Yes, up to `max_attempts_per_call` | The final error after the last attempt |
| Any other exception | No, exactly one attempt | `Error during tool execution: <Type>: <message>` |
| Invalid arguments / no schema / oversized | No, never executed | `Error: invalid arguments for ...` |
| Not on the allowlist | No, never executed | `Error: tool '...' is not on the allowlist` |
| Budget refusal | No, never executed | `Error: tool call refused — <stop reason>` |
| Consequential without approval | No, never executed | `Error: approval required ... no side effect was executed` |
| Cached result | Not executed again | The recorded result |

Only failures a tool author explicitly marks as retryable are retried.
Retrying an unknown exception risks repeating a side effect whose first
attempt partially succeeded.

### Stop reasons

`StopReason` values: `completed`, `max_turns`, `cancelled`,
`deadline_exceeded`, `call_budget_exceeded`, `tool_call_limit`,
`token_budget_exceeded`, `circuit_open`.

The first refusal sets `ExecutionBudget.stop_reason` and it is never cleared
for the rest of the run. `AgentRunResult.stop_reason` is the loop's own
reason; `AgentRunResult.budget.stop_reason` is the guard's. They can differ,
and when they do the budget is the more specific explanation — for example, a
loop that ended on `max_turns` after its tool circuit opened reports
`max_turns` for the loop and `circuit_open` for the budget.

Which reasons stop the manual loop immediately? `cancelled`,
`deadline_exceeded`, `call_budget_exceeded` and `token_budget_exceeded`.
Per-tool refusals (`tool_call_limit`, `circuit_open`) are fed back to the
model, which may still answer from what it already has. The LangGraph path
always sees a refusal as an error observation and continues until it answers
or reaches `recursion_limit`.

### Idempotency and approval keys

`action_key()` resolves in this order:

1. an explicit `idempotency_key` argument;
2. the model's call id, as `call:<id>`;
3. a truncated SHA-256 of the tool name and sorted arguments.

Precedence matters. A model that retries an action usually generates a new
call id, so only an explicit key survives that. The argument hash is a
convenience for read-only tools; a side-effecting tool should require an
explicit key, because two legitimate calls with identical arguments would
otherwise collapse into one. `create_support_ticket` requires the key.

`SqliteIdempotencyStore` writes only the completed textual result, keyed by
`(tool, key)`, with `INSERT OR IGNORE` for first-writer-wins. It is not a
distributed lock: two processes racing the same key can both execute the
tool, and only the first committed result is retained. That is a real limit,
not a guarantee of exactly-once execution.

Approval is explicit state. A call that needs approval records the action key
in `ApprovalStore.pending`, returns an error observation, and performs no side
effect. A caller then approves the key (`guard.approvals.approve(tool, key)`)
and the next call may run. This is not an interactive LangGraph interrupt:
nothing pauses mid-run waiting for a person. A consequence of that choice is
that approval must be granted before the call, or between runs.

## The A01 divergence

| Path | Before A03 | After A03 |
|---|---|---|
| Manual loop | Exception caught, error observation, loop continues | `ToolGuard` catches it, returns an error observation, loop continues |
| LangGraph | Tool node re-raised, run ended | `GuardedTool` returns an error `ToolMessage`; the tool node passes it through; the model continues |

The A01 test that pinned the re-raise (`test_graph_tool_exception_propagates`)
is replaced by `test_graph_tool_exception_becomes_observation`, and the shared
behaviour is also covered by
`tests/test_bounded_execution.py::TestGraphBounds::test_graph_returns_an_error_observation_for_an_unexpected_exception`.

## Alternatives considered

### LangChain middleware for the graph path

LangChain 1.x offers `ToolCallLimitMiddleware` and `ToolRetryMiddleware`.
They would bound the graph, but the manual loop would still need its own
implementation — a second policy, which is how the divergence appeared. They
also do not provide schema refusal, approval or idempotency. Rejected in
favour of one shared layer.

### Patch the graph's tool node

Catching the exception in a custom tool node would close the recovery
divergence but leave the manual loop with different validation, retry and
budget behaviour. It would also couple the solution to a LangGraph internal
node shape. Rejected.

### Keep the divergence and document it

The A03 brief allowed this if the difference were explained precisely. It was
not chosen: the shared guard makes the graph path recover without special
cases, so the stronger claim is also the simpler implementation.

### Process-based isolation

A per-call process would make the timeout enforceable (a thread cannot be
killed). That is a larger change than this task and belongs with K01's
isolation work. The current limit is documented rather than hidden.

## Limits

- **A timed-out tool is not killed.** The guard stops waiting; the daemon
  thread may continue. A non-cooperative tool can keep running after its
  result is discarded, and it can still perform its side effect late. The
  timeout is a bound on the run, not on the process.
- **Model latency and spend are not bounded here.** The provider client owns
  its timeout. `max_observation_tokens` estimates tool-output size from
  characters (`ceil(len/4)`), not tokenizer output, and is a context bound,
  not a billing measure.
- **Invalid calls count as failures.** Three consecutive invalid or failing
  calls to one tool open its circuit. This is intentional (fail closed), but
  it means a model that repeatedly hallucinates the same bad call is stopped
  even though no tool ever ran.
- **The allowlist refusal is not counted.** It is recorded as `refused` but
  consumes no budget slot, by design, so an invented tool name cannot use up
  a legitimate call's budget.
- **Default idempotency is in-process.** It is lost on restart unless a
  `SqliteIdempotencyStore` is supplied, and even then it is single-host.
- **The guard is not a sandbox.** It does not restrict filesystem, network or
  process access. It decides which calls may run, not what a running tool can
  do.
- **`MemorySaver` is still in-process.** Durable conversation state is a
  separate task; A03 does not change it.
- **The graph's `recursion_limit` remains a separate bound.** It limits model
  steps that make no tool calls; it is not a tool-execution budget.

## Acceptance criteria

| Criterion | Evidence |
|---|---|
| A slow or repeated tool cannot run indefinitely | `test_tool_guard.py::TestTimeouts`, `TestCircuitBreaker`; `TestSimpleLoopBounds::test_call_budget_stops_the_loop` |
| An invalid call cannot execute | `TestValidation::test_invalid_arguments_do_not_execute`; `test_bounded_execution.py` invalid-argument tests for both paths |
| A retry/restart of the same action produces one logical result | `TestIdempotency` (same key, same call id, new guard over the same SQLite file); `TestGraphBounds::test_replay_produces_one_logical_result` |
| The recorded reason for stopping is visible | `AgentRunResult.budget.stop_reason`, `BoundedAgent.budget`; asserted in `test_call_budget_stops_the_loop`, `test_circuit_breaker_stops_repeated_failures` and the graph budget test |
| The A01 divergence is closed | Both paths convert an unexpected exception into an error observation; see the replacement test and the graph test above |
