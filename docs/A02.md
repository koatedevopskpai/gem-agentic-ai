# A02 — Durable, correctly scoped memory

Status: implemented on `task/A02-durable-memory`, based on A03
(`90716a2`). This document records the design, the restart semantics, the
ownership boundary and the limits. The code comments describe how the store
works; this describes what the task does and does not establish.

## Why

`MemorySaver` keeps conversation state in a dictionary. When the process
exits, every conversation is gone. That is acceptable for a demo and not
acceptable for anything a user can resume.

There was a second gap: a LangGraph checkpoint is keyed by whatever
`thread_id` the caller puts in the config. Nothing checked who the thread
belonged to. A service that accepted a thread id from a request could resume
another user's conversation by accident or by design. The task asks for both
durability and correct scoping, so the two are solved together.

## What was built

| Component | Responsibility |
|---|---|
| `DurableMemory` | Owns the directory, the SQLite connections, thread config minting, deletion, retention and the guard factory |
| `_ThreadRegistry` | Maps `(user_id, thread_key)` to an opaque, random storage id; records creation and last-use times |
| `_ScopedCheckpointer` | A `BaseCheckpointSaver` that authorises every read and write against the registry |
| `memory.guard()` | A `ToolGuard` whose idempotency records live beside the checkpoints |
| `ThreadAccessError` | Raised when a config is missing a scope or names a thread the user does not own |
| `ThreadRecord` | A frozen record returned by listing and sweeping |

### Files

```
<directory>/
├── checkpoints.sqlite       # LangGraph checkpoints and pending writes
├── checkpoints.sqlite-wal   # SQLite WAL (and -shm) while open
├── thread-registry.sqlite   # ownership and retention metadata
└── idempotency.sqlite       # completed tool actions (A03 store)
```

The registry uses a separate connection from the checkpoint store. SQLite's
own locking plus `busy_timeout` serialises the two connections; neither
calls into the other's connection from a different thread.

### Why is the storage id opaque?

`thread_key` is the caller's name for a conversation ("support-1"). It is not
the primary key in the checkpoint store. On first use, the registry mints a
`uuid4().hex` storage id and returns a config containing it:

```python
{"configurable": {"thread_id": "<32 hex chars>", "user_id": "alice"}}
```

Knowing another user's thread key therefore does not reveal a usable
`thread_id`. The scoped checkpointer additionally verifies that the pair in
the config matches the registry row, so a guessed storage id is not enough
either.

## Ownership

The boundary is enforced in `_ScopedCheckpointer`, at every operation the
graph performs:

| Method | Check |
|---|---|
| `get_tuple` | `user_id` present, `thread_id` present, pair registered |
| `list` | same |
| `put` | same; also touches `last_used_at` |
| `put_writes` | same; also touches `last_used_at` |
| `delete_thread` | always refuses |

Deletion is not exposed on the checkpointer because `delete_thread(thread_id)`
carries no user context. The only route is `DurableMemory.delete_thread(user_id,
thread_key)`, where the user is part of the lookup.

**Threat model.** This enforces separation between *correctly identified*
users. It assumes the application supplies the authenticated user id to
`DurableMemory.config()`. If an application lets a caller choose their own
`user_id`, the boundary is only as strong as that input. The checkpointer
cannot authenticate a user; it can only refuse a config that does not match
the registry.

**Not covered.** A user with filesystem access to the directory can read the
SQLite files directly. At-rest encryption, per-user database files, and
OS-level access control are outside this task.

## Restart and resume

LangGraph writes a checkpoint at step boundaries (after the model node and
after the tool node, not inside a tool). On restart, `invoke` calls
`get_tuple` first and resumes from the most recent checkpoint. The messages a
reopened agent sends to the model are the evidence that state survived; the
test `test_conversation_survives_a_process_restart` asserts exactly that
across two `DurableMemory` instances.

### What is restart-safe

| Operation | Guarantee |
|---|---|
| Reading a conversation | Safe. The checkpoint file is opened and read. |
| Continuing a conversation | Safe. The same `(user_id, thread_key)` resolves to the same storage id. |
| Thread listing and ownership | Safe. Registry rows are committed on creation. |
| Deleting a thread | Safe and idempotent. A second delete returns `False`. |
| Retention sweep | Safe and idempotent. Only threads older than the cutoff are removed. |
| Completed tool actions | Safe while the idempotency store is SQLite-backed. `memory.guard()` uses it by default. |

### What needs reconciliation

| Situation | What can happen | What to do |
|---|---|---|
| Process killed during a tool call | The last checkpoint has the model's request but no tool result. The step is replayed on resume. | A consequential tool with a stable key is de-duplicated by the idempotency store. Tools without a stable key are at-least-once. Give them one, or reconcile externally. |
| Crash after the side effect, before the idempotency write | The action happened but is not recorded, so a replay repeats it. | This is the classic dual-write window. Reconcile against the downstream system using the action key before replaying. |
| Approval was granted in the old process | Approval is in an in-process `ApprovalStore` and is lost. | The action is refused with `approval_required`; approve it again. Deliberate: a human decision should not be silently inherited by a new process. |
| Deleting a thread | Checks are removed, then the registry row. A crash between the two leaves an orphan registry row with empty state. | Re-run `delete_thread`; it removes the row. The thread cannot leak state because the state is already gone. |
| Two hosts opening the same directory | SQLite file locking does not span a network filesystem, and SQLite is not a distributed lock. | Not supported. Use one host, or replace the saver with a server-backed one. |
| `ainvoke` / `astream` with this checkpointer | The sync saver has no async implementation; LangGraph would raise. | Unsupported in A02. Use the sync methods, or use `AsyncSqliteSaver` with the same scoping wrapper in a later task. |

The important consequence: **the memory is durable, but a hard crash can
repeat work.** A02 narrows that window for actions that carry an idempotency
key. It does not claim exactly-once execution across an arbitrary external
system; that needs the downstream system's cooperation.

## Retention

- `retention_days` defaults to 30 and must be positive.
- `last_used_at` is set on creation and updated by `config()` and by every
  checkpoint write, so an active conversation does not expire.
- `sweep_expired(now=...)` deletes threads idle longer than the cutoff and
  returns the deleted records for audit. It is explicit: opening the store
  never deletes anything. A scheduler is an operational concern, not hidden
  behaviour.
- Retention is per thread, not per message. There is no compaction of old
  messages inside a live thread; a long-running thread grows with its
  conversation.

## Alternatives considered

- **One JSON file per thread.** Simple to inspect, but no atomic multi-key
  writes, no ordering, and rebuilding LangGraph's pending-write model is
  work the SQLite saver already does.
- **A thread id that embeds the user** (`alice:support-1`). It looks
  scoped, but any caller can construct one; nothing verifies that the
  prefix is true. It also leaks the user id into logs and checkpoint keys.
- **A `user_id` convention, checked only at the call site.** A single missed
  check resumes a foreign conversation. Enforcing it inside the saver
  means the graph cannot read or write without the pair.
- **A server-backed checkpointer (Postgres/Redis) now.** More moving parts,
  credentials and a paid service. The task is local and free; the scoped
  wrapper is saver-agnostic in principle, and a server saver can be
  substituted later.
- **Auto-sweep on open.** Convenient and surprising. Deletion should be
  observable and schedulable, so the sweep is a method.

## Acceptance criteria

| Criterion | Where it is proved |
|---|---|
| Conversation state survives a process restart | `TestRestartAndResume::test_conversation_survives_a_process_restart` (two instances over one directory) |
| Another user cannot read it | `TestOwnership` — `get_tuple`, `invoke`, and `list` all raise `ThreadAccessError`; `test_thread_list_shows_only_the_owners_threads` |
| Another thread cannot read it | `TestThreadIsolation::test_threads_do_not_share_state` |
| Replay does not repeat a completed side effect | `TestReplayAfterRestart::test_a_completed_action_is_not_repeated` (two instances, one ledger entry) |
| Deletion behaviour | `TestDeletion` — owner can delete, another user cannot, state is gone, id can be re-created empty |
| Retention behaviour | `TestRetention` — only idle threads are swept; opening does not delete; non-positive retention is rejected |
| Restart-safe vs reconciliation is documented | This document, the two tables above |

## Limits

- Sync checkpointer only; async graph calls are not supported by this version.
- One local SQLite file, one host. No distributed coordination.
- Ownership depends on the application supplying an authenticated user id.
- The directory is not encrypted; anyone with filesystem access can read it.
- A tool without a stable idempotency key remains at-least-once across a
  crash, and the dual-write window is not closed.
- The retention sweep covers whole threads only.
