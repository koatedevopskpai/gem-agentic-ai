## What changed

- `src/gem_agentic_ai/api/` — `server.py`, `streaming.py`, `auth.py`,
  `sessions.py`, `__main__.py`.
- `streaming.py` — one-turn service: token forwarding, per-turn deadline,
  cancellation inside the task iterating the graph, rollback of an
  unanswered user message, and `ThreadedTurn`, which runs each turn on a
  dedicated event loop in a worker thread.
- `server.py` — FastAPI app: session CRUD, SSE turn endpoint, bearer-token
  authentication, `404` for another user's session, `409` for a second
  concurrent turn, `422` for invalid messages and deadlines. The per-session
  claim is released when the turn's cleanup is complete — by the response
  once the worker's closing sentinel arrives, or by the worker itself when
  the response has already ended (a disconnect). It is not released merely
  when the HTTP response ends.
- `agent/graph.py` — `BoundedAgent.astream` closes the inner graph
  generator explicitly so a cancelled consumer unwinds LangGraph promptly.
- `persistence.py` — `_ScopedCheckpointer` gained `aget_tuple`, `alist`,

### Latency detail

Twenty turns, six scripted tokens each, one token every 50 ms:

| Measurement (Linux) | Median | p95 |
|---|---|---|
| Client first token | 64.27 ms | 67.67 ms |
| Client total | 328.90 ms | 350.83 ms |
| Server first token | 58.47 ms | 60.05 ms |
| Server total | 321.62 ms | 344.25 ms |
| Client-observed overhead beyond server timing | 5.80 ms | 7.28 ms |

The scripted cadence (6 × 50 ms = 300 ms) dominates by construction. The
last row is the API's share: request handling, SSE framing, loopback
transport and client parsing. **No provider was called**, so these are not
model latency figures. The Windows run measured 5.26 ms / 6.49 ms overhead on
the same scenarios.

### Disconnect and timeout detail

- Disconnect: the client read 3 tokens and closed the response. The model
  had emitted exactly 3 tokens for that turn when cancellation arrived, and
  still 3 after 300 ms — the token count is frozen. History was empty
  (`awaiting_reply: false`), and the next turn on the same session returned
  `recovered`.
- Timeout: `deadline_seconds: 0.15` produced `event: error`,
  `code: timeout`, after 2 tokens; the model's stream was cancelled and
  history was empty.
- Resume: after an abandoned turn, the model context for the next turn
  contained the first exchange (`My name is Alice.`) and did not contain the
  abandoned question. The session claim is released by the cancelled
  worker after its rollback, so a resume issued while cleanup is still
  finishing gets `409` and is retried; the client is not left to race it.
- The tests and the demo give an abandoned turn a dedicated httpx client
  and close it. Reusing a connection whose SSE body was only partly read
  delivers the tail of that body as the next response; that was observed
  while writing the resume scenario (the resumed answer was the abandoned
  turn's own tokens) and the dedicated client removes it.

## How cancellation was proved

The test double records whether its `_astream` was cancelled and how many
tokens it emitted. The assertions are:

- `model.cancelled is True` — cancellation reached the model's stream.
- `model.emitted` did not increase after cancellation (sampled 100–300 ms
  later) — the model is not still producing.
- history is empty and `awaiting_reply` is false — the rollback ran.
- a follow-up turn completes — the session was not left locked.

The server tests run behind a real uvicorn socket; the streaming test drives
`ThreadedTurn` on a plain loop. Both assert these properties, so a
regression in the ASGI path or in the class is caught separately.
